# Bridge answers 404 (Nov 24): what to check on the VPS

For ChatGPT (or a person) working on the VPS behind `zarkhaiz.duckdns.org`. Do not print, change or share the
bridge token. Do not change the bridge's API, its port or the Muse bridge.

Symptom: from a Claude cloud session that sends the bridge token, `GET https://zarkhaiz.duckdns.org/health` and
`GET https://zarkhaiz.duckdns.org/jobs` both return 404. The Muse inbox under `/muse-bridge/` is a different service and
must keep working.

1. Is the ChatGPT bridge running?
   `systemctl --user list-units | grep -i bridge`, `systemctl list-units | grep -i bridge`, `ps aux | grep -i bridge`.
   If it is stopped, start it and enable it at boot (`systemctl [--user] enable --now <name>`), then read its log
   (`journalctl [--user] -u <name> -n 50`).
2. Does it answer locally? `curl -s http://127.0.0.1:<its port>/health -H "Authorization: Bearer $TOKEN"` (the token
   from its own config; do not print it). Expected: JSON with `"images": true`.
3. Does the web server route to it? In the Caddy (or nginx) config for `zarkhaiz.duckdns.org`, the paths `/health`,
   `/jobs` and `/jobs/*` must go to the bridge's port, next to the `/muse-bridge/*` route. A config that now sends
   everything except `/muse-bridge/*` elsewhere (or nowhere) gives exactly this 404. Add the routes, then
   `caddy validate` and `systemctl reload caddy` (or `nginx -t` and `systemctl reload nginx`).
4. Test from outside: `curl -s -o /dev/null -w "%{http_code}" https://zarkhaiz.duckdns.org/health -H "Authorization: Bearer $TOKEN"`
   must print 200, and `https://zarkhaiz.duckdns.org/muse-bridge/health` must still work.

Report in short Roman Urdu: what was wrong, what changed (file and line), and the two test results.
